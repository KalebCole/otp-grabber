# Issue #9: retaining Messages Full Disk Access across app updates

Research date: 2026-10-16. Scope: [issue #9](https://github.com/KalebCole/otp-grabber/issues/9). This is a proposed implementation and verification plan; the permission-retention result still needs a test on the target Mac.

## Finding

The strongest documented cause is the app's **ad hoc signature**. Apple says macOS uses a signed app's *designated requirement* (DR) to recognize it across versions for privacy authorization. An ad hoc signature has a DR tied to that particular code version, so macOS cannot reliably carry an authorization to the next version. Apple's example concerns microphone permission, so applying the same outcome to this app's Full Disk Access grant is a strong inference, **not yet a measured fact**. For this personal Mac project, a **stable self-signed Code Signing certificate** is the viable no-fee identity to test. Apple says self-signed certificates can establish that two versions came from the same source, though they are unsuitable for ordinary public distribution. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements); [Apple Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html).

The current [build script](https://github.com/KalebCole/otp-grabber/blob/main/scripts/build-menubar.sh) fixes the bundle identifier at `com.otpgrabber.menubar` and executable name at `OTPGrabberMenuBar`, then runs `codesign --force --deep --sign -`. That `-` is Apple's ad hoc pseudo-identity, which provides no reusable signing identity. [Apple's ad hoc signature reference](https://developer.apple.com/documentation/security/seccodesignatureflags/adhoc). The [installer](https://github.com/KalebCole/otp-grabber/blob/main/scripts/install-menubar.sh) targets `~/Applications/OTP Grabber.app`, deletes the old bundle, and copies the new one. The path should remain stable for updates, but deletion itself has **not** been isolated as the permission-loss cause. The [release workflow](https://github.com/KalebCole/otp-grabber/blob/main/.github/workflows/release.yml) calls the same ad hoc build path. The [setup guide](https://github.com/KalebCole/otp-grabber/blob/main/docs/LOCAL-MAC-SETUP.md) currently assumes eventual Developer ID signing; this research adds a no-fee local alternative.

Apple lists Messages among the app data covered by Full Disk Access. The user must grant Full Disk Access in System Settings; the app cannot grant it to itself with an entitlement or code. [Apple Support](https://support.apple.com/en-au/guide/mac-help/mchl211c911f/mac); [Apple Developer Documentation](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox).

## Recommended implementation

1. **Create one personal signing identity and keep its private key safe.** Apple's documented manual route is **Keychain Access → Certificate Assistant → Create a Certificate**, with **Self Signed Root** and **Code Signing** selected. The identity can also be generated with equivalent certificate extensions and exported as a password-protected `.p12` for CI. Do not regenerate the certificate for each build: a new certificate is a new code identity. [Apple Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html); [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/).
2. **Sign every personal release with the same identity.** The release build uses the public certificate fingerprint pinned in `signing/identity.sha1` to select its signer and verifies the packaged app against that certificate and `com.otpgrabber.menubar`. It fails if the identity is missing or mismatched. Development builds may remain ad hoc signed, but are not suitable for permission-retaining updates. A default or explicit DR can tie updates to the same certificate and signing identifier; compare the DRs of two release builds on the target Mac. [Apple Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html); [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/).
3. **Keep the private key out of Git.** The one-time setup exports a password-protected `.p12`, keeps an encrypted backup outside GitHub, and puts the `.p12` and its password in encrypted GitHub Actions secrets. The tagged-release workflow imports the identity into a temporary keychain on a disposable macOS runner. Only the public fingerprint is committed. This makes the build recipe durable in the repo while keeping private material out of source control. [GitHub's certificate import guide](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications); [GitHub's secrets guide](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets); [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
4. **Keep the install destination fixed and make replacement safe.** Stage and validate the new signed app before stopping the installed app; replace the same path only after validation and retain a rollback copy until the updated app launches. This is a repository-specific reliability recommendation based on the current install script, not a claim that copying in place by itself preserves TCC access. Avoid re-signing an already signed app with a different identity on the target Mac; that may change its DR. [Current installer](https://github.com/KalebCole/otp-grabber/blob/main/scripts/install-menubar.sh); [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
5. **Handle denied access in the app.** The current [Messages reader](https://github.com/KalebCole/otp-grabber/blob/main/menubar/Sources/OTPGrabberMenuBarCore/MessagesReader.swift) maps SQLite `EACCES`/`EPERM` to `.accessDenied`, and the [menu-bar model](https://github.com/KalebCole/otp-grabber/blob/main/menubar/Sources/OTPGrabberMenuBar/App.swift) displays its recovery text. Make that state specific: identify the installed `OTP Grabber.app`, tell the user to open **System Settings → Privacy & Security → Full Disk Access**, enable or re-add that exact app, then quit and reopen it. Optionally provide an **Open Full Disk Access Settings** button; Apple Developer Technical Support shows `x-apple.systempreferences:com.apple.settings.PrivacySecurity.extension?Privacy_AllFiles` for macOS 13+. Do not treat a generic database error as proof of denied FDA. [Apple Developer Forums](https://developer.apple.com/forums/thread/791996); [Apple Support](https://support.apple.com/en-au/guide/mac-help/mchl211c911f/mac).

**Migration caveat:** the first move from today's ad hoc build to self-signed signing changes the DR, so an existing grant may need to be made once for the newly signed app. The goal is retention across *subsequent* releases with that stable certificate. This is an inference from Apple's DR behavior and must be checked on the target Mac. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).

## Target Mac verification (no message content in the record)

Use two consecutive local builds signed with the **same self-signed identity**, at the **same installed path**. Capture metadata before installing either update and again afterward. Run the following in Terminal on the Mac; the commands display app identity only, not Messages data:

```bash
app="$HOME/Applications/OTP Grabber.app"
/usr/libexec/PlistBuddy -c 'Print :CFBundleIdentifier' "$app/Contents/Info.plist"
/usr/libexec/PlistBuddy -c 'Print :CFBundleExecutable' "$app/Contents/Info.plist"
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "$app/Contents/Info.plist"
/usr/bin/codesign --display --verbose=4 "$app" 2>&1 | /usr/bin/grep -E '^(Identifier|TeamIdentifier|Authority|Signature|Executable)='
/usr/bin/codesign -d -r - "$app" 2>&1 | /usr/bin/grep 'designated =>'
/usr/bin/codesign --verify --deep --strict --verbose=2 "$app"
```

Record the installed path, macOS version, app version, identifier, executable name, signer/Authority, DR, and signature verification result for each candidate. A self-signed identity may have no Apple TeamIdentifier, so a missing TeamIdentifier is not by itself a failure. Compare the *requirement*, not merely the certificate display name. Apple documents `codesign -d -r-` for inspecting the DR and describes how to compare code signatures across variants. [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/); [Apple Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html).

Before the update, verify that the installed app can retrieve a fresh inbound Messages test code and that its Full Disk Access entry is enabled. Install the next signed build over the same app, quit/relaunch it, and repeat both checks **without touching the grant**. In the test record use only `Messages read: success/denied/other`, the setting's enabled state, and the identity metadata above. Never include the actual message, sender, code, database rows, screenshots containing private data, or TCC database contents. A successful pre-update read plus a successful post-update read without regrant is the acceptance proof requested in [issue #9](https://github.com/KalebCole/otp-grabber/issues/9); checking the System Settings toggle alone is insufficient.

If the post-update read fails, compare the before/after DR and certificate identity first, then verify which app path was launched and whether a different copy is present. If the signatures match but access still fails, capture the app's high-level `.accessDenied`/other error classification and macOS version for a narrower investigation; avoid resetting or editing TCC as part of routine diagnostics. Apple's general file access guidance notes that mandatory access control behavior can vary with the protected location and macOS release. [Apple Developer Forums: On File System Permissions](https://developer.apple.com/forums/topics/app-and-system-services/app-and-system-services-core-os).

## Alternatives and limits

- Keeping ad hoc signing while only changing the install copy operation is unlikely to solve repeated authorization: Apple explicitly says its DR is version-specific. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
- A self-signed certificate is a **local identity**, not Developer ID. Apple says a self-signed certificate is useful for development/internal testing and should not be shipped as a normal public distribution signature. It cannot be notarized: Apple's notary service rejects self-signed apps. A downloaded or otherwise quarantined app may be stopped by Gatekeeper; the user can use **System Settings → Privacy & Security → Open Anyway** for an app they trust. Do not disable Gatekeeper globally or remove quarantine as the routine setup. [Apple Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html); [Apple notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues); [Apple Support](https://support.apple.com/en-ie/102445).
- A future public release with normal Gatekeeper acceptance would require Developer ID signing and notarization, which Apple says require paid program membership. Source distribution that users build and sign locally is the no-fee alternative Apple Developer Technical Support identifies for other users. [Apple Developer Forums](https://developer.apple.com/forums/thread/761393?answerId=799007022); [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
- No app code can silently regrant Full Disk Access. Even with stable signing, the user may have to act if they revoke the grant or macOS no longer recognizes the installation. The exact behavior after this project's update must be measured on the target Mac. [Apple Developer Documentation](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox); [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).
